# Scheduled Jobs

Scheduled jobs let a Chat channel ask Sidekick to perform recurring autonomous work. This document records the agreed product behavior and the architectural boundaries for implementing it.

## Model

A **scheduled job** belongs to one Chat channel and contains:

- An autogenerated, stable integer ID used for management. IDs start at 1 within each channel, increase monotonically, and are never reused.
- A required human-readable name.
- An optional description.
- A required schedule.
- A required IANA timezone.
- A required prompt.
- Whether the job is enabled, defaulting to `true`.
- An optional `last_run_at` timestamp, absent until the first run is claimed.

A **scheduled run** is one firing of a scheduled job. Job identity links runs for management and observability; it does not create conversational continuity.

## Management

Users manage scheduled jobs through conversation with Sidekick in the owning channel. Sidekick needs agent tools to:

- Create a job.
- List the channel's jobs.
- Update a job.
- Pause or resume a job.
- Delete a job.

Job mutations require an explicit request directed at Sidekick. Passive channel conversation must not create or change jobs.

The owning channel is the management and delivery boundary. Cross-channel management is not part of the current scope.

Scheduled-job management uses the existing rules for who may invoke Sidekick in a channel. There is no creator ownership or job-specific authorization model.

## Active-job limit

A channel may have at most five active jobs. An active job is one whose `enabled` field is `true`.

Any mutation that would leave the channel with more than five active jobs is rejected without changing state. This applies when creating an enabled job and when enabling a paused job. Disabled jobs do not count toward the limit.

Job names are unique within a channel, including disabled jobs. Name comparison is case-insensitive. Stable IDs remain the unambiguous identifier for management operations.

## Scheduling

The required schedule families are:

- Every hour.
- Every day at a specified time.
- Every week on a specified day of week and at a specified time.

The persisted schedule uses a cron expression. Sidekick translates conversational schedules such as "every weekday at 09:00" into cron; users do not need to write cron themselves.

The cron dialect is the standard five-field format:

```text
minute hour day-of-month month day-of-week
```

Jobs have minute-level precision. Seconds are not accepted or persisted. An implementation using Spring's six-field cron parser supplies a fixed zero seconds field at the scheduler boundary.

The job stores a required IANA timezone, such as `Europe/London`, separately from the cron expression because cron does not define one.

The cron expression is evaluated directly in the stored timezone using that zone's daylight-saving rules. Sidekick must not convert and persist the schedule as UTC; doing so would shift the intended local execution time when daylight-saving offsets change.

If a scheduled local time does not exist during a daylight-saving transition, that occurrence is skipped. It is not shifted or caught up later.

Repeated local times during a daylight-saving transition receive no custom handling. The scheduler's normal timezone behavior applies, subject to the one-hour cooldown.

## Due runs and cooldown

When an enabled job is loaded or changed, the scheduler calculates its next occurrence strictly after the current time. Occurrences missed while Sidekick was stopped are discarded; they are not run after restart and are never replayed.

When a scheduled occurrence arrives, it is eligible only when:

- `last_run_at` is absent or earlier than the scheduled occurrence; and
- At least one hour has passed since `last_run_at`.

Every job has a fixed one-hour cooldown regardless of its cron expression. A schedule may express more frequent occurrences, but Sidekick must not start that job more than once per hour.

There is no separate overlap guard. If a run lasts longer than the cooldown, a later eligible occurrence may start another isolated run of the same job.

Before starting Sidekick, the scheduler atomically claims the due occurrence by setting `last_run_at` to the current time. Claiming before agent execution prevents repeated scheduler scans or concurrent scheduler activity from starting the same occurrence twice.

Despite its name, `last_run_at` records when a run was claimed for execution, not when it completed successfully.

## Running Sidekick

Every firing creates a fresh, isolated Session and executes one full Sidekick Turn using the job prompt as its current instruction.

The run:

- Has the normal Sidekick system prompt and configured model behavior.
- Has access to the normal tool registry, including available skills, subagents, MCP tools, and bash when configured.
- Receives the owning channel's metadata and channel-scoped project context, including its project `AGENTS.md` when present.
- Has its own session-scoped history and work area.
- Does not inherit messages, Koog history, compactions, settings, attachments, or work files from earlier runs of the job.

A scheduled firing is a first-class Turn trigger. It must not be represented as a fabricated inbound Chat message or pass through reply-admission rules intended for human messages.

## Delivery

A successful run posts its final answer as a new root message in the owning channel. It never posts the result as a thread reply.

The Chat adapter remains responsible for platform-specific delivery. Scheduled-job orchestration deals in Sidekick's Chat, Session, and Turn concepts rather than Slack payloads.

Agent or delivery failures use Sidekick's existing Turn failure behavior, posted as a root channel message.

A failed run is not retried automatically. Because the occurrence was claimed before execution, failure consumes that occurrence; the job waits for its next eligible scheduled occurrence.

## Persistence

Configured jobs are durable, channel-scoped state under `agent.state-directory`:

```text
<agent.state-directory>/slack/channels/<channel-id>/jobs.jsonl
```

The file contains the channel's current configured jobs, one job per line. It is machine-managed state, not a user-edited configuration file and not an append-only event log.

A small channel-local sequence file persists the last allocated ID so deleting the highest-numbered job cannot cause its ID to be reused.

Run-specific Session state remains separate from `jobs.jsonl` and uses a unique identity for every firing.

## Runtime boundaries

The scheduler reads persisted jobs and initiates due runs. Creating or changing a job must take effect without adding static Spring configuration or restarting Sidekick.

Job storage should sit behind a dedicated port. It is not part of conversation state: conversations and scheduled jobs have different identities and lifecycles even though both are stored beneath the configured state directory.

The existing fixed weekly statistics reporter is separate legacy behavior. It does not define the execution model for user-configured scheduled jobs.

Scheduled runs use the existing Turn execution limits. There is no job-specific timeout, run-history store, or audit subsystem. `last_run_at` and ordinary Session state are sufficient for the initial feature.

## Implementation outline

### Domain and persistence

- `ScheduledJob` is the persisted model containing `id`, `name`, `description`, `schedule`, `timezone`, `prompt`, `enabled`, and `last_run_at`.
- `ScheduledJobRun` identifies one claimed firing and carries its channel and job through orchestration.
- `ScheduledJobStore` is the persistence boundary for listing and mutating channel jobs and atomically claiming a due run.
- `FilesystemScheduledJobStore` stores the current records in each channel's `jobs.jsonl`.
- `ScheduledJobService` owns create/update/delete validation, name uniqueness, the five-active-job limit, cron and timezone validation, and due-run claiming.

### Agent tools

One `ScheduledJobTools` tool set exposes four tools. Every tool is scoped implicitly to the current channel.

#### `scheduled_jobs__create`

Inputs:

- `name` — required.
- `description` — optional.
- `schedule` — required five-field cron expression.
- `timezone` — required IANA timezone.
- `prompt` — required.
- `enabled` — optional, defaults to `true`.

Returns the created job. It rejects invalid cron or timezone values, duplicate names, and creation of a sixth active job.

#### `scheduled_jobs__list`

Takes no inputs. Returns all enabled and disabled jobs for the current channel, including the active count and limit.

#### `scheduled_jobs__update`

Inputs:

- `job_id` — required.
- Any mutable job fields: `name`, `description`, `schedule`, `timezone`, `prompt`, or `enabled`.

Returns the updated job. `id` and `last_run_at` are not user-editable. An empty description clears it. Enabling a job enforces the active-job limit; renaming enforces channel name uniqueness.

#### `scheduled_jobs__delete`

Takes `job_id` and returns the deleted job's ID and name. Deletion is permanent.

There are no separate pause, resume, get, validation, or manual-run tools. Pause and resume are updates to `enabled`; listing at most five active jobs makes a separate get tool unnecessary.

### Scheduler and execution

- `ScheduledJobsScheduler` evaluates enabled jobs at minute precision in their stored timezones.
- It asks `ScheduledJobService` to atomically claim eligible occurrences before dispatching them.
- `RunScheduledJobUsecase` creates a unique fresh Session for the claimed run and invokes scheduled Turn execution with the job prompt.
- Scheduled Turn execution bypasses inbound-message admission and reply classification but reuses normal prompt construction, agent execution, tools, persistence, and failure handling.
- A Slack result handler posts replies and failures to the channel root.

### Runtime flow

```text
conversation -> ScheduledJobTools -> ScheduledJobService -> ScheduledJobStore

scheduler tick -> ScheduledJobService.claim -> RunScheduledJobUsecase
               -> fresh Session -> agent Turn -> root channel reply
```

### Module placement

- `core`: scheduled-job model, service, store port, filesystem store, and scheduled Turn execution boundary.
- `tools`: `ScheduledJobTools` and registration in the normal Slack-backed tool registry.
- `app`: Spring Scheduling adapter, run use case, and Slack dispatcher/root-message delivery adapter.
